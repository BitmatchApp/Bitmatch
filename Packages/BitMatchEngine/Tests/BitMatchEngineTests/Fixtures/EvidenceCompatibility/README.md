# Evidence compatibility corpus

All media bytes are tiny, original synthetic payloads, generated by `Scripts/ascmhl/create_compatibility_fixtures.py`. No camera footage, personal hostname or production metadata is included. The fixtures and handcrafted reports/classic-MHL example are offered under BitMatch's MIT license.

`reference/` was generated with the official [ASC MHL reference implementation](https://github.com/ascmitc/mhl) at commit `0fb61f1e4c7c1c3ff422449aa6f091ce0d3b7687`, with additions on October 14 and 17, 2026. Its MIT notice is retained in `ASC-LICENSE.md`. The manifests are output from that tool, not BitMatch's writer. MD5 and MD5-renames contain two generations; the other datasets contain one. Each inventory and chain passed the official XSDs, `ascmhl-debug verify` and `ascmhl diff`. The CLI's own timestamp/version fields are retained; the hostname is replaced before generation.

Regenerate into a new, empty directory using a Python 3.11+ environment with that pinned checkout installed:

```
python Scripts/ascmhl/create_compatibility_fixtures.py /tmp/new-bitmatch-evidence-fixtures
```

The tests copy fixtures into disposable roots. MD5/XXH64, zero-byte files, Unicode/XML escaping, filename whitespace, nested roots and two generations must retain every expected path. Changed/missing media must fail; additional files are informational. C4-only entries are explicitly unsupported, including beside supported records. Tests derive corrupt, duplicate, unsafe-path, failed-action, foreign-namespace, future-version, prefixed-namespace, entity and nested-metadata variants without changing these originals.

`reports/` captures current, older, extended, Quick, unsafe, unknown-method, unknown-algorithm and truncated JSON. Only current and compatible extra-field snapshots may supply a verified saved-report status. These handcrafted snapshots test reader compatibility; they are not fresh verification evidence or output attributed to an external offload application.

October 14 additions use the same pinned reference commit and license: `sha1/` and `xxh128/` are valid external inventories that BitMatch must explicitly reject as unsupported, both alone and beside a readable history. `xxh64-boundaries/` contains original byte sequences (`byte[index] = index % 251`) of lengths 0, 1, 31, 32, 33, 255, 256, 257 and 1025, covering XXH64's lane and tail boundaries. These fixtures passed the independent checks below; their Swift consumer regressions also passed on Mac.

October 17 addition: `md5-renames/` is another output of the same pinned reference CLI, generated with `create -h md5` and then `create -h md5 -dr`. Between those generations, one synthetic file is renamed and `Reel B` is renamed to `Reel C`. The second manifest records two file `<previousPath>` values and one directory `<previousPath>`; the reference verifier and diff accept the final folder, while a further unrecorded directory move fails. BitMatch Check deliberately rejects this history as unsupported until it can interpret rename lineage and structure. It does not call the old paths missing or claim to have verified the chain. The media payloads and fixture script are original/MIT; the reference-tool output retains its MIT notice in `ASC-LICENSE.md`.

Run the corpus checks on Linux or macOS without Swift, using the reference venv:

```
python Scripts/ascmhl/validate_corpus.py /path/to/pinned/ascmitc/mhl
```

The runner requires the pinned, unmodified checkout, uses its code and schemas, suppresses the CLI's online update check, and checks inventory/chain schemas, generation counts, C4 chain digests, bytes and paths. It checks changed, missing, renamed, extra, modified-manifest and missing-manifest cases only in disposable copies, requiring specific failure codes. A rename must report both the new and missing path. SHA-1/XXH128/C4 file hashes are verified by the reference tool here, not claimed as supported file digests by BitMatch. Originals must remain byte-for-byte unchanged. `validate_reference.sh` runs this subset as well as the Apple-only freshly generated BitMatch workflow. The corpus-only runner is also a Linux CI job.

Generate just new datasets without replacing existing originals using `--datasets sha1 xxh128 xxh64-boundaries md5-renames`. Default generation creates all seven datasets. Generation suppresses the reference CLI's online update check as well.

`classic-v1.mhl` is a handcrafted boundary fixture, not external-tool output. It is rejected inside an ASC history both alone and beside a valid reference history; standalone classic-MHL 1.1 content checks were added on October 20 (see below). Check's supported inventory-chain scope is described below; directory hashes, rename lineage and historical authenticity remain outside it. Histories are never rewritten by these checks.

October 19 original-format addition: [`classic-reference/`](classic-reference/README.md) contains three original tiny media files and a sanitized classic MHL 1.1 inventory generated by the unchanged, MIT-licensed original reference CLI at `pomfort/mhl-tool@34f06f22ae965d12e49590adc301373d5ce611ff`. Its six MD5/SHA-1 digest records pass independent Python and CryptoKit checks, the original v1.1 schema and reference-tool verification. The retained MIT notice, exact commands, schema hashes and disposable negative controls are documented there. This originally expanded attributable input/boundary coverage. The October 20 reader uses it for standalone classic content checks, without mapping generic hashes to a BitMatch verification tier or writing histories.


October 19 addition: `reference/bitmatch-fat-extended/` is a **sanitized derivative** of the actual engine's initial FAT-v1 history generated by `ASCMHLFixture` on a disposable mounted exFAT image. The real mounted sample separately passed official extension/verification/diff with its original status unchanged. For the public fixture, the initial hostname was replaced with `bitmatch-fixture-host` and the synthetic clip filename changed to ASCII `Camera A/clip.txt`, and its exact v1 single-generation chain/status was rebuilt during fixture creation only. The pinned official `ascmhl create -h md5 -i '._*'` then appended generation two to that sanitized copy; this is not a byte-for-byte mounted-volume capture. The first media payload comes from the original/MIT fixture executable; `added.txt` is original synthetic text. The new reference output retains the ASC MIT notice above. The official CLI hostname is the synthetic `bitmatch-fixture-host`. Its explicit metadata pattern excludes only test-volume AppleDouble companions from this portable dataset; it does not define BitMatch's production filtering policy. No existing fixture was rewritten.

Both manifest schemas, the chain schema, two ordered reference C4 digests, original media verification and inventory diff passed independently. The first-generation `BITMATCH_HISTORY_STATUS.txt` is byte-identical after the official extension. Run `python Scripts/ascmhl/validate_fat_chain_fixture.py /path/to/pinned/ascmitc/mhl` in its Python 3.11+ venv to revalidate the immutable v1 witness, schemas, C4, media/diff and a modified-inventory negative control without editing the originals. The Swift reader tests this fixture plus missing, replaced, reordered, malformed and unsupported generations; it checks chain records, not directory hashes or historical authenticity. Valid custom basenames are supported. Removing a self-consistent unanchored tail cannot be detected as a custody violation and is expressly not claimed.

Regenerate a new sanitized derivative with `python Scripts/ascmhl/create_fat_chain_fixture.py /path/to/pinned/reference /path/to/new/initial-only/ASCMHLFixture-output /tmp/new-fat-extended-fixture`. The input must contain only the fixture tool's known synthetic media and a complete initial FAT-v1 history. It is never edited; output must not exist. The script sanitizes before the official append and asserts that append leaves the sanitized initial witness unchanged.

The ASCII derivative name is deliberate: the mounted sample exposed a composed/decomposed Unicode filename mismatch after Git materialization. Production path handling and the existing external Unicode corpus were not changed. The independent FAT harness also runs against a fresh Git archive of the committed fixture, rather than relying on APFS's Unicode-equivalent lookup in the creation directory.

October 20 reader coverage: standalone UTF-8 classic MHL 1.1 is read-only input to Check, after supported BitMatch reports and ASC evidence. Every MD5/SHA-1 digest and recorded size is required; conflicting inventories, changed evidence, symlinks and cancellation fail closed. Classic XML inside `ascmhl/` remains unsupported rather than being mistaken for an ASC history. Synthetic reader tests add whitespace/Unicode, zero-byte media, bounded parsing, interrupted reads and named-file replacement. These are not additional reference-generated fixtures, full XSD validation, signature verification or a transfer safety verdict.
