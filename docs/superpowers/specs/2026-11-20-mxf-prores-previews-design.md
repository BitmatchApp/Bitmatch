# MXF ProRes report previews

Date: 2026-11-20. Branch: fix/mxf-report-previews. Follow-up to #91 (reporter: Codex Compact Drive, ProRes MXF; reports show no clip previews).

## Intent

Reports with "Clip previews" on show a frame for ProRes clips in an MXF wrapper (ARRI ALEXA family; Panasonic and Canon ProRes MXF expected but unmeasured), the way they do for `.mov` and `.mp4` today.

## Why it does not work today, and cannot via AVFoundation

`ReportThumbnailService` asks AVFoundation (`AVAssetImageGenerator`) for a frame. Measured on macOS 27 with Apple's Pro Video Formats installed: every third-party AVFoundation client fails to open an MXF with "Cannot Open" (command-line tool, unsandboxed app bundle, sandboxed app bundle, Intel build under Rosetta); Apple's own `avmediainfo` fails too. QuickTime Player opens the same file. Apple's MXF reader is a MediaToolbox format-reader plug-in (`AppleMXFImport.bundle`, x86_64 only, 2007–2020) that only Apple's apps get. No BitMatch version has ever produced an MXF preview; the extension was not listed until this branch, and listing it alone changes nothing.

## What works (spike on the ARRI sample F003C002, 1080p ProRes 4444, and on ffmpeg-made files)

MXF is a flat sequence of KLV packets (16-byte SMPTE key, BER length, value). The first picture essence element (key prefix `06 0E 2B 34 01 02 01 01 0D 01 03 01 15`, generic-container picture) sits within the first few dozen packets, well under 1 MB in. Its value is one complete ProRes frame: a self-describing bitstream starting with a 4-byte frame size and the `icpf` tag, carrying width, height and chroma format in its own header. VideoToolbox's public ProRes decoder (`VTDecompressionSession` with a format description of type `ap4h` for 4:4:4 or `apch` for 4:2:2) decodes that frame to a pixel buffer. The ARRI frame decoded to 1920×1080 in milliseconds; a 64×64 one-frame ffmpeg MXF (7.7 KB) parses and decodes identically.

## Goals

- A verified ProRes MXF clip on the backup gets a preview in the PDF, under the existing caps (200 previews, 30 s total, 2 s per clip, 64 KB per image, 256×144).
- No third-party code. The MXF reading is a bounded in-house scan; decoding is VideoToolbox.
- A clip the scan cannot handle gets no preview, exactly as an unsupported clip today, with nothing else affected.

## Non-goals and anti-goals

- Not a general MXF demuxer: no index tables, partitions, descriptors, audio, timecode or metadata. First picture frame only.
- Not Sony XAVC (H.264/HEVC in MXF), ARRIRAW, DNxHD, or clip-wrapped essence with no ProRes header at the start. Those stay without previews (ARRIRAW is not a ProRes bitstream; XAVC is a follow-up on the same shape).
- Never read more than a bounded prefix of a file; never decode more than the pixel cap (40 MP: one BGRA buffer of ~160 MB if a decoder ignores the output-size request, plus the copied compressed frame of at most the 64 MiB cap and the decoder's own working set) and never hold more than the frame cap of compressed bytes; never let a preview failure touch transfer evidence, as today.

## Approaches

1. **Bundle an open-source MXF library (libMXF, or ffmpeg's demuxer).** Full container support, but C code inside a sandboxed, notarized Swift app, licence and build burden, and far more surface than a thumbnail needs. Rejected.
2. **Own bounded KLV scan + VideoToolbox decode.** About two hundred lines, pure Swift, testable with a 7.7 KB fixture; decoding uses Apple's own ProRes decoder. Chosen.
3. **Tell users MXF previews are not possible.** True for AVFoundation, false in general. Rejected.

## Design (approach 2)

**Engine, pure Swift, no media frameworks:** `MXFFrameLocator` in `BitMatchEngine`.

- `static func firstPictureFrame(descriptor: Int32, fileSize: UInt64, scanLimit: UInt64 = 64 MiB, packetLimit: Int = 4096, frameLimit: UInt64 = 64 MiB, shouldContinue: () -> Bool) -> MXFFrame?` where `MXFFrame` is `(offset: UInt64, length: UInt64)`. The caller opens the file once, takes `fstat` size from that descriptor, locates the frame, and reads the frame bytes with `pread` from the same descriptor, so the path is never reopened (the same shape as `ClipIntegrityCheck`, which closes the symlink and size window `collect` checks by path). A URL convenience wraps open/fstat/close for tests.
- All offsets and lengths are `UInt64` with overflow-checked arithmetic (`addingReportingOverflow`); any overflow, any offset or end past `fileSize`, the indefinite BER form (`0x80`), and any BER length field longer than 8 bytes is malformed: nil. Non-minimal long-form lengths (leading zero bytes) are accepted. A zero length is valid for a non-picture packet (SMPTE ST 377-1 KLV fill items) and is skipped; a zero-length picture value is nil. A BER length of `FF FF FF FF FF FF FF FF` is simply "past end of file".
- Reads headers only (one 25-byte read at each packet start: the 16-byte key plus the longest legal BER length field; for a short packet the tail of that read may land inside the value, and those bytes are never interpreted) with `pread`, and skips values; it never reads value bytes except the first four of the picture value (the ProRes frame size) and never the frame itself; see the frame-length rule for the 8 bytes it does read. Stops at the first picture element, at `packetLimit` packets, at `scanLimit` bytes, at end of file, at the first malformed packet, or when `shouldContinue()` is false (checked before every packet; the caller passes the per-clip deadline), returning nil.
- Run-in: MXF allows up to 64 KiB of run-in before the header partition pack. The locator reads the first `min(64 KiB, fileSize)` bytes once (the only read that is not a packet header or the 8-byte frame prefix) and begins the scan at the first occurrence of the partition pack key prefix `06 0E 2B 34 02 05 01 01 0D 01 02 01 01` in it; if absent, nil.
- Picture element match: the first 13 key bytes equal `06 0E 2B 34 01 02 01 01 0D 01 03 01 15`; bytes 14–16 (count, element type, element number) are not compared.
- Frame length: the locator reads the picture value's first 8 bytes (the only value bytes it reads): the ProRes frame size (big-endian) and the `icpf` tag. Without the tag, or with a frame size under 32, nil at the locator boundary, so a non-ProRes MXF never causes a frame read. The frame length is that size when it is at most the KLV value length (frame-wrapped: equal; clip-wrapped: smaller, so the first frame of the clip); when it is larger than the KLV length, nil. `frameLimit` applies to this frame length, not to the KLV value length, so a clip-wrapped value of any size still yields its first frame. (ARRI and ffmpeg both write frame-wrapped essence; measured: the ffmpeg fixture's first picture value is exactly one frame.)
- Only the file given is ever looked at; if the picture element is not in this file (OP-Atom audio or index file), nil.

**Shared, VideoToolbox:** `ProResFrameDecoder` next to `ReportThumbnailService`.

- `static func image(frame: Data, maximumSize: CGSize) throws -> CGImage?`
- Validates the header: `frame.count` is at least 32; the frame size at bytes 0–3 is at most `frame.count` (the decoder is given exactly that many bytes, so KLV padding is dropped) and at least 32; bytes 4–7 are `icpf`; the header size at bytes 8–9 is at least 20 and `8 + headerSize` is at most the frame size; width and height at 16–19 are 16 to 8192 each and width × height at most 40 megapixels (ALEXA 65 is 20 MP, 8K is 33 MP); the chroma format (byte 20, bits 7–6: `10` is 4:2:2, `11` is 4:4:4) is one of those two. Anything else: nil (no decode attempted). The decoded buffer is the real memory cost, not the compressed frame, so this cap is checked before any session exists.
- Asks the decoder for the preview-sized output buffer directly (`kCVPixelBufferWidthKey`/`HeightKey` at the fitted size under 256×144) so the full-size BGRA frame is never materialized in this process; measured on the ARRI frame. If a decoder ignores the request, the frame is still under the pixel cap and is downscaled after.
- Codec type `ap4h` for 4:4:4, `apch` for 4:2:2 (the decoder accepts any ProRes 4:2:2 profile under that type; measured with an LT-profile frame). A frame with alpha still decodes; the preview drops alpha.
- Builds a `CMVideoFormatDescription`, a `CMSampleBuffer` over a `CMBlockBuffer` that owns a copy of the frame bytes (so the buffer's lifetime is the sample's, not the caller's `Data`), and a `VTDecompressionSession` with BGRA output; decodes synchronously with the output-handler form; fits the result inside `maximumSize` preserving aspect and never upscaling, and returns the `CGImage`. The session is invalidated in a `defer` and the whole decode runs inside an `autoreleasepool`; no caching.

**Wiring:** the extraction closure gains the row's recorded size: `extract: (URL, TimeInterval, Int64) async throws -> Data?`. `ReportThumbnailService.frame(_:timeout:expectedSize:)` dispatches by lower-cased extension: `mxf` goes to a new `mxfFrame(url, timeout, expectedSize)`; everything else keeps the AVFoundation path, which ignores the size. Failures are swallowed exactly as today. The decode passes empty flags (no asynchronous or temporal processing) so the output handler runs before the call returns.

The file is opened once with `open(O_RDONLY | O_NOFOLLOW | O_NONBLOCK)`, checked with `fstat` to be a regular file, located and read with `pread` (retrying `EINTR`, looping on short reads) from that one descriptor, and closed in a `defer`; no `FileHandle` (its errors are Objective-C exceptions). This happens inside the same `collect` call and security scope that the AVFoundation path uses today, so access lifetime is unchanged.

MXF work is synchronous (`pread` and a VideoToolbox decode that takes milliseconds), so it cannot be abandoned mid-call the way an AVFoundation request can. It therefore runs on one shared serial queue for all MXF previews, not a per-request queue, with **bounded admission**: a request is submitted only when the worker is idle (an atomic busy flag set on submission, cleared when the block finishes); while the worker is busy, a new MXF request returns nil at once with no pending closure. So there is never more than one MXF block in flight or pending, across repeated collections. One worker may stay blocked indefinitely on a wedged volume; callers still finish promptly, that worker's late result is discarded (the continuation completes exactly once, at the deadline), and MXF previews are simply absent until it returns.

Access (lead ruling): the worker runs under the exporter's existing read lease on the destination root, the same lease the AVFoundation path relies on; the destination URL is rebuilt from the row's path and cannot start a scope of its own, and plumbing the root bookmark into the preview service is not worth a corner that already fails safe. An orphan that outlives the lease finds its reads refused and returns nil; its result would be dropped anyway. Before opening, it verifies the deadline; after `open` it verifies with `fstat` that the descriptor is a regular file **and that its size equals the row's recorded size** (the same value `collect` checked by path, now bound to the opened file); the deadline is checked again between read retries and before decoding. The dispatch onto that queue is `async`, never a `sync` bridge from a per-request queue, so a wedged read costs one thread and the MXF previews of this process, not a thread per clip. The caller awaits with the existing timer and continuation pattern: at the deadline it resumes with nil and moves on; the orphaned work finishes on its own and its result is dropped. The block queued on the shared queue checks the deadline before opening the file and again before decoding, and the locator's `shouldContinue` is the same deadline, checked between packets, and the frame read is bounded by `frameLimit`, so an orphan that keeps making progress stops at the deadline, one that is wedged in a system call holds at most one frame cap of bytes plus one decode, and either way exactly one exists. Cancellation of the whole collection stops the next clip as today.

**iOS:** VideoToolbox exists on iOS; the same code compiles there. No iOS-specific behavior.

## Fixtures and tests

- `tiny-prores.mxf` (7.7 KB, ffmpeg, 64×64, one orange ProRes LT frame) as a base64 constant in the engine tests and the Shared tests, the way `previewFixture` is today. Nothing from ARRI enters the repo.
- Engine: locator finds the frame in the fixture at the known offset and length, through the descriptor API; `readFrame` takes the same `shouldContinue` and stops between retries; picture values of 1–3 bytes are nil; returns nil for a non-MXF file, a truncated file, a file whose first packet claims a 2 GB value, a frame whose length runs past end of file, a file with 5000 non-picture packets, an empty file; never reads past `scanLimit` and reads no value bytes other than the returned frame (a counting reader asserts bytes read ≤ headers + frame). BER coverage: a hand-built packet with a short-form length (under 128), one with a long-form length, and one with the 8-byte all-`FF` length; a sparse file whose picture value is in-file but larger than `frameLimit` with a frame-size field also over the limit (nil) and one whose frame-size field is under the limit (first frame returned); a hand-built clip-wrapped value (two frames in one KLV) returns the first frame's size; a file with 70 KiB of run-in before the partition pack (nil) and one with 1 KiB (found); a zero-length fill packet before the picture element is skipped; an indefinite BER `0x80` length is nil; a 9-byte length field (`0x89`) is nil; a length field truncated by end of file is nil; a long-form length with a leading zero byte is accepted; a picture value whose frame size is 0, or whose tag is not `icpf`, is nil; a frame size larger than its KLV length inside a longer file is nil; `shouldContinue` returning false after N packets stops the scan with nil.
- Shared: decoder returns a 64×64 image for the fixture frame whose center pixel is orange (R > 200, G between 80 and 200, B < 80); a 64×48 ffmpeg fixture returns an image with a 4:3 aspect; an HQ-profile (4:2:2) frame and the LT frame both decode under `apch`; nil for a frame whose tag is not `icpf`, for every truncated prefix of the fixture frame from 1 to 31 bytes, for a frame-size field larger than the data, for a header claiming 8000×8000 (64 MP, rejected by the pixel cap alone) and one claiming 16384×16384 (rejected before any session), for an empty `Data`.
- Shared, worker contract (a test seam `ReportThumbnailService.mxfWorkerHook`, run on the worker before opening, lets a test block it on a semaphore): with the worker blocked, a second MXF request returns nil immediately (bounded admission); the blocked request returns nil at its deadline; releasing the block afterwards publishes nothing (no late image, continuation completed once); the next request after release succeeds. A request whose `expectedSize` differs from the file returns nil before any read. A request for a FIFO (`mkfifo`) returns nil (not a regular file). After a preview, `collect`'s returned `requestedCount` and the caller's `results` array are unchanged (evidence invariance through the MXF path). Scope lifetime is not unit-testable outside the sandbox; the orphan-fails-nil behavior is covered by the deadline test and documented above.
- Shared: `ReportThumbnailService.collect` with a verified `.mxf` row whose backup is the fixture produces a JPEG under 64 KB, and so does a `.MXF` row; a `.mxf` row pointing at a non-ProRes MXF (a hand-built MXF whose picture value is not a ProRes frame, bytes synthesized in the test, no ffmpeg) produces no image and no error; a zero-timeout MXF request returns nil without decoding; a cancelled collection does not start the next MXF clip.
- Opt-in real media: `BITMATCH_ARRI_SAMPLE=/path/to/F003C002_190925_MN99.mxf` runs the full path on the ARRI clip and asserts a 256×144 JPEG within the 2 s per-clip budget.
- Mac suite and engine suite green; `./test.sh ipad-test` runs the decoder tests on the iPad simulator, not only the build.

## Accepted limits

- Anamorphic or non-square-pixel clips preview at the stored pixel aspect (squeezed); the descriptor is not read.
- No color metadata is set on the format description; a preview may differ slightly in tone from a graded view. Previews are decoration.
- Panasonic and Canon ProRes MXF are expected to share the generic-container picture key, but only ARRI and ffmpeg output were measured.
