# One-time re-copy after failed verification — October 21, 2026

Remainder of `docs/TODO.md` "Output ownership and recovery". Builds on
failed-readback marking (`<name>.bitmatch-failed`, see
`failed-readback-marking-2026-10-21.md`): a marked file proved the
attempt's own output was corrupt, so instead of only reporting the
failure, the attempt now retries that one file once and only trusts it
if the retry itself verifies.

Source: worktree `wt-recopy`, branch `todo/recopy-20261021`.

## Behavior

- Trigger is narrow: a checksum mismatch on a file this attempt wrote,
  proven by a non-nil marking outcome from the marking step. Reused
  files (never marked), read errors (verification throws instead of
  mismatching), and Quick mode (no readback, no marking) never enter
  re-copy. Exactly one re-copy runs — there is no retry loop.
- The bad file is marked first, under the existing identity proof, so
  corrupt bytes are never at the normal name when the retry publishes.
  The retry copies the single file to the single failed destination
  (`DestinationWriter.copyAllSafelyFanOut`, one worker, pre-enumerated
  source) and verifies it again from the pinned destination root,
  including clip inspection.
- Success is claimed only when the re-copy verifies. The result row
  then reports success with `recopyOutcome = "recovered"` while the
  initial `failedOutputMarking` outcome is preserved, and History
  wording is "recovered after one re-copy (first copy failed
  verification)". Verified coverage (`workMeter.verified`) is credited
  only for a recovered success.
- If the retry also mismatches, it is marked again under the same
  identity rules — normally `nameOccupied`, because the first bad file
  already holds the `.bitmatch-failed` name, so the second bad file
  stays at its normal name and is never claimed good. The row stays
  failed with `recopyOutcome = "stillFailed"` and History adds
  "re-copy also failed". A changed source simply fails the second
  verification; it is never silently trusted.
- Cancellation during re-copy propagates as cancellation. Other
  re-copy errors (copy failure, verification throw) degrade to
  `stillFailed` with the initial verification and marking preserved.
- `ResultRow.recopyOutcome` is Codable with a legacy-safe optional
  decode, so pre-existing History records load unchanged.

## Fault matrix

| Fault | Outcome |
| --- | --- |
| One-time copy-stream corruption (Thorough) | Marked, re-copied, verified, recovered |
| Corruption repeats on the retry | Second file left at normal name (`nameOccupied`), still failed |
| Destination bytes flipped/truncated/replaced after copy | Recovered by verified re-copy, initial marking preserved |
| Destination file deleted after copy | Read failure, not proven corruption: no marking, no re-copy, stays failed |
| Read error during readback | Throws out of verification: no marking, no re-copy |
| Quick mode | No readback exists, so no marking and no re-copy |

## Limits

- A missing destination file is deliberately not re-copied: absence is
  a read failure, not proof the attempt's bytes were corrupt, and
  external deletion is tamper evidence the operator should see.
- Recovery is per file and per failed destination only; it does not
  repair from a verified sibling copy. Sibling repair still needs its
  recovery-provenance design (revalidate sibling, independently verify
  the repaired destination, retain repair evidence) and remains open.
- Fault coverage is synthetic (test hooks and planted corruption). A
  physical media smoke on the merged code copied the seeded 305 MB
  card fixture (151 files) from the SD card (`/Volumes/Untitled`) to
  the T9 (`/Volumes/T9`) through the real engine in Thorough mode:
  309 result rows, 0 failed, verdict successful, 7.6 s, with
  independent byte comparisons matching. That exercises real media
  read/write paths only — it is not a signed-app walkthrough and it
  injected no fault on physical media. The three-disk
  `Scripts/test-physical-drives.py` suite later ran with a third
  volume (WheeDrive) attached and passed; see
  `physical-three-disk-2026-10-21.md`.
