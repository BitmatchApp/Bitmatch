# Main-actor drive-access review — October 21, 2026

This is a source audit of the remaining drive-access boundary called out in the [volume probe record](volume-mount-probes-2026-10-20.md) and [TODO](../TODO.md#next-five-bounded-slices). It is not a runtime reproduction: no app, build, test, simulator, drive, or filesystem-stall probe was run for this review. A blocked synchronous filesystem call cannot be cancelled by cancelling its Swift task or by letting a display deadline expire.

## Findings, by responsiveness impact

1. **Queue presentation performs repeated identity reads on MainActor.** `SharedAppCoordinator.queuePresentation` loops over every session record and calls `prepareSourceForEjection`, then checks Mac ejectability, before it builds the row presentation ([SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L1592)). `prepareSourceForEjection` resolves a persisted bookmark, starts security-scoped access, reads directory/volume/resource identity and readability, and validates that the original folder is still present ([TransferJournal.swift](../../Packages/BitMatchEngine/Sources/BitMatchEngine/TransferJournal.swift#L375)). The property is read by the queue view and its eject handler, the Dock badge, and coordinator summary/eject helpers ([TransferQueueSection.swift](../../Shared/Views/TransferQueueSection.swift#L52), [DockTile.swift](../../BitMatch/App/DockTile.swift#L130)). Progress and view updates can therefore repeat disk and bookmark work for all rows, including rows that are not eligible for ejection. This is the clearest likely hot path; runtime impact has not been measured.

2. **Selection setters synchronously identify and bookmark selected folders.** `SharedAppCoordinator` is MainActor-isolated. Assigning `sourceURL` constructs `LocalTransferResource`; assigning `destinationURLs` does so for each new destination and also resolves each volume label ([SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L375)). The resource initializer reads resource values and creates a security-scoped bookmark ([TransferJournal.swift](../../Packages/BitMatchEngine/Sources/BitMatchEngine/TransferJournal.swift#L23)); label resolution requests volume metadata ([ResultPresentation.swift](../../Shared/Core/Models/ResultPresentation.swift#L362)). Mac's separate bounded mount-identity probe does not cover these operations.

3. **Admission performs filesystem preflight and journal resource creation synchronously.** The Setup enqueue action calls `enqueueSelection` on MainActor ([CoordinatorSetupLocations.swift](../../Shared/Views/Setup/CoordinatorSetupLocations.swift#L295)). It validates selected resource identities, then calls `BackupTargetPolicy.refusal`, `SafetyValidator.validateResolvedDestinationRoots`, and `CardSource.containsRegularFile`; the last enumerates the source tree ([SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L1136), [SafetyValidator.swift](../../Packages/BitMatchEngine/Sources/BitMatchEngine/File/SafetyValidator.swift#L377), [CardSource.swift](../../Packages/BitMatchEngine/Sources/BitMatchEngine/File/CardSource.swift#L181)). `enqueue` then constructs another resource and bookmark for every selected URL before committing the journal ([TransferJournal.swift](../../Packages/BitMatchEngine/Sources/BitMatchEngine/TransferJournal.swift#L321)). Queued-edit admission repeats root and nonempty checks. `startOperation` also performs composer identity validation synchronously after its asynchronous independence check ([SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L1825)).

4. **Mac launch restore and permission recovery resolve bookmarks synchronously.** MainActor `MacVolumeAccessModel.init` calls both saved-destination restore and bookmark loading ([MacVolumeAccessModel.swift](../../BitMatch/Core/ViewModels/MacVolumeAccessModel.swift#L44)). Destination restore checks existence and volume facts, then adds each result through the shared destination policy and setter ([MacVolumeAccessModel.swift](../../BitMatch/Core/ViewModels/MacVolumeAccessModel.swift#L551)). Saved bookmark loading resolves bookmarks, checks existence and starts access; the legacy path may analyze each volume ([MacVolumeAccessModel.swift](../../BitMatch/Core/ViewModels/MacVolumeAccessModel.swift#L451)). After the access panel returns, its MainActor callback creates the bookmark, writes it to Keychain and UserDefaults, and starts the scope ([MacVolumeAccessModel.swift](../../BitMatch/Core/ViewModels/MacVolumeAccessModel.swift#L376)). These are potential blocking boundaries from source inspection only.

5. **Saved-record preparation is synchronous at several user-visible actions.** Queue replay calls `staleResourceIndexes` and then `prepareToRun` before the first suspension; both resolve and validate saved resources. Editing a queued setup calls `prepareToRun` synchronously. The History reauthorization status wrapper resolves and validates every saved URL synchronously ([SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L1203), [SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L1680), [SharedAppCoordinator.swift](../../Shared/Core/Services/SharedAppCoordinator.swift#L1727)). This merits a later bounded-worker change alongside the admission boundary.

## Queue-presentation fix proposal

Keep the presenter pure: have `queuePresentation` read a cached `mountedSourceIDs` value rather than open bookmarks or read a drive. Reconcile only session records that are both terminal and `safeToErase`; other states cannot expose eject. Schedule reconciliation when session membership or journal record state changes, when the Mac volume monitor publishes a mount/unmount/replacement update, and after eject. Coalesce to the latest generation, cap active and waiting work (for example, the existing two-active/eight-waiting bounds), and serialize work for one lexical mount while allowing another mount to proceed. Apply a completion only when the generation, record ID, and original source identity still match. Pending, unavailable, and replaced sources stay absent from the cached set, so no eject affordance appears until identity is confirmed.

Cached presentation state is not authorization. `ejectQueueSource` must still resolve and validate the recorded source immediately before ejection, retain its security-scope lease through the eject call, and reject a replaced folder. Run that final blocking preparation on the same bounded worker so an eject tap cannot perform synchronous identity reads on MainActor. Worker deadlines may update UI state, but a worker slot stays occupied until its filesystem call returns. This proposal does not weaken the existing verified-result, source-identity, or internal-drive rules.

Current invalidation is only implicit because the coordinator rereads the filesystem for each presentation. Journal `refresh()` invalidates the completed-row derivation cache, not mount status; queue-session add/remove/retry/recovery paths update IDs and order; eject adds the ID to `ejectedQueueSourceIDs`; the Mac monitor's connected-volume publisher is currently handled in `MacVolumeAccessModel`, without a queue mount-state cache. A cached replacement must explicitly invalidate on these sources of change and fail closed while reconciling.

## Focused validation for a future implementation

Existing coverage to retain:

- `QueueSummaryCacheTests.completedEvidenceIsReusedAcrossLiveTicksAndSourceChanges` checks that the pure journal presenter responds to changing mounted/ejected ID inputs. It does not exercise coordinator bookmark reads or mount-cache invalidation.
- `LocalTransferQueueIntegrationTests.testReadableReplacementAtSamePathIsNeitherCountedNorEjected` and `testOutcomeEjectUsesFinishedJournalSourceNotLiveSelection` protect original-folder identity and record-source selection.
- `LocalTransferQueueIntegrationTests.testInternalSourceDoesNotOfferOrAttemptBulkEjection` and `testEjectAllSafeCardsSkipsUnsafeRowsContinuesAndReportsFailures` protect ejection eligibility and per-card failure behavior.

Add focused held-worker tests before changing the coordinator: repeated queue presentations make zero synchronous resource/bookmark calls; safe terminal records reconcile within active/waiting bounds; a held mount does not block a healthy second mount; same-mount jobs serialize; unmount, same-path replacement, record mutation/removal, queue reorder, ejection, and stale late results cannot publish a mounted ID; pending or failed identity never offers ejection; and the final eject preparation rejects replacement while retaining/releasing the access lease on every path. Keep one deliberate MainActor-regression test for queue presentation and one for the eject handler. Run only the focused app-host queue/volume suites when the compiled gates are released; these tests establish behavior for their injected fixtures, not real removable-drive responsiveness.

## Implementation follow-up — October 21, 2026 (candidate; validation pending)

The current source candidate adds a shared `DriveAccessWorker` that accepts bounded jobs reserving a set of lexical mount keys. It admits at most two active jobs and eight queued jobs; work for any mount already held by an active job waits behind that job. Cancelling a caller settles its wait, but a synchronous filesystem operation already underway keeps its worker slot and mount reservation until it returns. Queue-full admission fails with `busy`; it does not create unbounded waiters.

Queue rows now read source availability from `SourceAvailabilityModel` rather than resolving bookmarks during each presentation. The model starts empty, reconciles only sources belonging to eligible session rows, groups records by lexical mount, and limits itself to two active groups. It keeps one pending group per distinct mount represented by the eligible records, so this pending list is bounded by the current queue data rather than by a separate fixed count. The shared worker admits at most eight queued jobs across all consumers. The model applies a result only when the generation and original resource key still match; record/journal changes, queue membership or ejected-state changes, and Mac mount notifications invalidate or reschedule the cache. Probe errors leave a source unavailable, and a busy group is retried after a short delay. The cache only controls whether the UI offers eject. `ejectQueueSource` still prepares and validates the journal's original source on the worker immediately before ejecting, checks that the saved record is unchanged and still safe, and retains/releases its access lease around the eject call.

Setup selection and admission now have prepared async paths. Source, destination, and replacement policy checks reserve the selected and compared mounts on the worker, then apply through expected-source/destination checks; UI request generations and cancellation prevent superseded picks from winning. `TransferSelectionPreparation` creates and validates the original resource identities on the worker. `enqueueSelectionPrepared`, `editSetupTransferPrepared`, `startSetupTransfersPrepared`, and the inline-card prepared path commit those exact resources through `LocalTransferJournal`; UI transitions occur after the durable result. Setup labels and capacity values are prepared with selection and read from coordinator caches during presentation.

History status checks, reauthorization, and retry/requeue now also use worker-backed journal methods. They reserve the stored source/destination mounts (and the replacement mount for reauthorization), keep record lookup on MainActor, and await an unstructured commit task so caller cancellation cannot hide a durable journal mutation. The reconnect view reports a failed status check as unavailable, keeps its stale-status value nil until a successful read, and releases a picked security scope when the worker operation finishes or when the view leaves while idle. Mac connected-destination presentation compares standardized lexical paths instead of resolving canonical paths during view construction.

These are implementation details from the current candidate, not validation results. Focused and full build/test gates are still pending. No app responsiveness measurement, deliberate blocked-mount run, simulator or physical-drive check is claimed. Lexical grouping does not establish physical-device identity; a blocked synchronous filesystem call remains uninterruptible and occupies its bounded worker slot until it returns. Mac launch restore and permission/keychain recovery remain separate boundaries from this candidate and require their own validation or follow-up.
