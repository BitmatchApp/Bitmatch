# Actual-app report memory hold — October 21, 2026

A retained Mac app-host stress run crossed its test memory guard while generating the requested PDF report for a 20,000-file transfer. This was a controlled local test failure, not an OS crash or a reproduction of field report #23. Later 40,000-row PDF probes isolated high memory during page rendering, but no bounded-memory production fix is established.

## Actual-app result

Gate `mac-manyfiles-20261021T053629Z` ran one selected `CoordinatorManyFilesMemoryTests` XCTest from source commit `6ca018015bc75427c3349b2177b9a34e1e37f6ba`. XCTest reported **one test, zero skips, one failure** after **763.822 seconds**. It created 20,000 synthetic 1 KiB source files and copied and verified them to two host-filesystem destinations, producing 40,000 result rows. Abstract disk identities made the two-destination workflow eligible; it is not independent physical-backup coverage.

The report-off transfer passed in **288.020 seconds**, with **2,281 active-view renders** and **1,572 progress updates**. The second transfer finished copy and verification before reporting began: the process monitor read **392 MiB** after copy and verification and **421 MiB** at `reportStarted`. The unchanged **1,024 MiB cooperative test guard** later latched at **1,099 MiB**; later diagnostic samples reached **1,309 MiB**. The test failed with `memoryLimit` and cancelled its owned work. ASC MHL and PDF thumbnails were disabled in both passes.

This establishes a guard crossing during the report-enabled phase after copy and verification. It does not establish which PDF subphase or allocation caused the crossing. A separate private test-only diagnostic recorder reported an error during the first report-off pass, before the second pass; its cause is unknown and it is not evidence of an app-startup or PDF failure. No default or user log was read or repaired. The failure fixture and evidence were retained.

## PDF phase experiments

The later scale gates used 20,000 synthetic filenames with two backup results (40,000 rows), a 1,024 MiB process guard, and the app's report renderer. They are focused synthetic probes, not actual transfer tests or reproductions of #23.

- The eager baseline, gate `mac-pdf-scale-20261021T104140Z` at commit `6f3b3c5`, built and measured the 40,004 report blocks at **155 MiB**, then peaked at **1,097 MiB** during `pageRender`. It produced **1,430 pages** and **82,501,213 bytes** before the unchanged guard failed in `finalPDFData`. The failure is a controlled test-guard failure.
- The synchronous lazy-factory experiment, gate `mac-pdf-scale-20261021T104340Z` at commit `f2d25da`, lowered page-render peak to **996 MiB**, but its *in-process full-document PDFKit text coverage check* peaked at **1,523 MiB**; the overall probe peaked at **1,535 MiB** and failed the same guard in `pdfCoverage`. This bulk extraction step belongs to test validation, not to report generation.
- The async buffered-render experiment, gate `mac-pdf-scale-20261021T105100Z` at commit `77196cc`, peaked at **1,030 MiB** during `pageRender` and failed the unchanged guard. The tested sleeps and cancellable batches did not bound the render peak. Cancellation tests for that candidate had not yet run at the time of this gate.
- The status-text-mark experiment, gate `mac-pdf-scale-20261021T105718Z` at commit `b32c247`, completed one generator pass at **1,000 MiB** against the **1,024 MiB** guard, producing **1,430 pages** and **72,591,335 bytes**. It is a narrow single-run pass, not evidence of comfortable headroom or a robust memory fix.
- The streamed-sink experiment, gate `mac-pdf-scale-20261021T110558Z` at commit `2337f5b`, completed one 40,000-row render in **107.611 seconds**, peaking at **985 MiB** against the unchanged **1,024 MiB** guard. It produced **1,430 pages** and **72,590,057 bytes**. This is another narrow single-run pass and is not sufficient evidence of a bounded-memory fix. An independent manifest receipt and visual review for this streamed artifact are not recorded here.

For the last gate, bulk manifest validation was moved to a separate Poppler process, so its memory is not part of the app-process generation measurement. The independent validator receipt reports all **40,000** expected backup filename occurrences across 1,430 pages: 20,000 for each backup, 20,000 source IDs checked, no missing/wrong copies, duplicate IDs, malformed tokens, row-label errors, empty pages, or Poppler warnings. It validates text coverage; it does not provide visual PDF quality assurance.

Focused PDF tests on commit `b32c247`, gate `mac-pdf-focused-20261021T110230Z`, completed **20 tests in two suites with zero skips and zero failures** in **1.646 seconds**. The corrected focused run on commit `6c75147`, gate `mac-pdf-focused-20261021T111040Z`, completed **22 tests in two suites with zero skips and zero failures** in **4.193 seconds**. An earlier run on `1880484` failed one test-harness assertion because Quartz's first callback was a full write; the injection was corrected to wait for a genuine partial write before simulating ENOSPC. The corrected test does not report an application PDF-write failure. Root visually inspected rendered pages 1, 715, and 1,430 from the `b32c247` artifact; sampled rows and footers were readable and aligned with no obvious clipping. This is a three-page spot check, not a review of every page or the streamed artifact. Focused regressions and the earlier text-mark candidate's single scale pass do not establish robust memory bounds.
