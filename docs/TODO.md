## Ranked work queue

This is the order to **investigate or start a bounded slice**, not a promise to ship in this order. It weighs everyday usefulness and safety against implementation difficulty, the blast radius of a mistake, and whether the result can ship and be tested independently. These are judgments, not measured scores. **Quick** means a contained change with local regression coverage; **scoped** means a defined feature or audit; **long** needs design, physical tests, or multiple stages; **demand** needs stronger user evidence. Blast radius means the potential effect on transfers, evidence or platform behavior, not the number of files edited. The detailed acceptance criteria remain in the sections below.

The two active reports come first as **casework**, but neither is a ready-to-ship fix: [#23](https://github.com/BitmatchApp/Bitmatch/issues/23) needs the reporter's version/phase or a reproduced memory path, and [#10](https://github.com/BitmatchApp/Bitmatch/issues/10) needs decisive diagnostics or a physical reproduction. Synthetic passes alone cannot close either report.

Unreleased work on `main`: terminal/History presentation, Mac card-event reconciliation, the verification wording audit's first slice, unknown-drive Setup wording, SFTP interruption/stale-evidence checks, the expanded MHL corpus, the Mac menu bar companion and per-drive I/O detail have landed. The engine test runner now executes both test frameworks. First-upload and subprocess-cancellation SFTP fixes remain in draft while their race cases are resolved; the menu bar and speed display still need a signed-app walkthrough before release. None of this closes the active user reports or replaces the physical checks below.

## P1 — Reliability and recovery

October 14 cloud progress: [the assurance audit](VERIFICATION_ASSURANCE_AUDIT.md) maps current source/destination reads, digests, evidence and wording gaps. The branch adds bounded saved-evidence reads and guards the combined photographer backup timestamp against rejected local evidence. The [Apple validation gates](CLOUD_RELIABILITY_HANDOFF.md) passed on the MacBook; neither P0 report nor the full audit acceptance below is closed.

The queue/recovery items marked complete below were merged in #20 for 0.2.8; see [validation and limits](QUEUE_RECOVERY_VALIDATION.md).

The priority buckets are not a strict implementation sequence: investigate P0 reports and audit assurance wording first, use physical benchmarks for default and scheduling decisions, and validate ASC MHL chains read-only before extending them. Source-read retry depends on fault classification and source identity; destination re-copy or repair additionally requires proof of output ownership. Neither retry path depends on MHL validation.

- [ ] **Close the exFAT/FAT media-file publication race.** The current no-hard-link fallback exclusively claims the final name, checks that it still owns the claim, then uses `renameat` to publish the verified temporary file. Another writer could replace that name between the check and rename; the failure cleanup has a similar check-then-unlink window. First turn adversarial publication cases into regressions for the current engine, then choose a no-overwrite design. Copying into the claimed descriptor is one candidate, but it makes an incomplete final-name file visible during interruption and needs an explicit recovery/presentation policy. Preserve the [thesis](THESIS.md)'s partial-copy promise. **Acceptance:** deterministic claim/replacement/rollback/interruption tests preserve any other writer's bytes and existing files; owned partial output stays unmistakably incomplete; actual exFAT/FAT and APFS runs confirm publication and recovery behavior; source media stays untouched and every uncertain result fails closed.

- [ ] **Make failed readback output unmistakable on disk.** BitMatch publishes a copied file at its normal destination name before readback; the existing corruption regression confirms that the bad file remains there even though the app verdict correctly fails closed. Investigate marking or moving only an attempt-owned, identity-checked file that fails verification. A read error does not prove the bytes are corrupt, and even bad bytes may be worth preserving. **Acceptance:** injected mismatch, read error, external replacement, interrupted marking and marking failure never overwrite, delete or relabel another writer's file; the real on-disk path and uncertainty appear in History/reports and recovery; source media stays untouched.

- [ ] **Verification coverage and default-policy audit.** Standard is the fresh-install default; a previously saved mode stays selected. Setup, History and PDF/CSV/JSON wording have been aligned with recorded checks, and Compare has its own check-plan wording. Still map Quick, Standard, Thorough and Paranoid to copy-stream source hashing, independent source rereads, destination readback, byte comparison, source-change checks, ASC MHL/report evidence and the actual safe-to-erase verdict. Include a one-time transient source misread and a repeatably wrong read: a second read can catch differing bytes, but cannot prove the original camera bytes or detect every stable fault. Treat the recommended default as a product choice informed by safety, user workflows and measured time; it may move up or down the assurance ladder, but every verdict must name the checks actually performed and the selected-file scope. **Acceptance:** finish-screen, README and Guide mode claims need a final check against the engine and fault-injection tests; Quick and intentionally excluded-file transfers stay unsafe; injected source and destination faults produce honest outcomes. Any default change has explicit behavior for fresh versus saved preferences, release notes and Mac/iPad/iPhone validation.

- [ ] **Separate local-source and remote-destination assurance.** A local source can be independently re-read before a later SFTP upload; the current Mac SFTP queue uploads an already verified local backup, not the card. Its SHA-256 readback downloads the remote file, while upload-only remains **Uploaded · Unverified**. The screen and report labels landed in #26; contract, interruption and stale-local-evidence tests have since landed. Keep local source reread, local backup verification, remote upload and remote readback as distinct facts in diagnostics and future changes. Do not infer source assurance from a remote readback or deny source assurance merely because a later destination is remote. **Acceptance:** no remote result becomes a whole-card safe verdict without the required local checks; the first-upload and child-cancellation drafts must also pass adversarial and live-server tests before merging. Apply the same evidence separation to any future cloud provider, with Mac-only SFTP scope explicit on iPad/iPhone.

- [ ] **Storage-aware verification scheduling.** Replace the CPU-derived default with scheduling informed by physical storage identity and measured behavior. Avoid competing large sequential reads on one HDD; permit useful concurrency across independent SSD/NVMe devices. Account for shared devices and buses only where reliably identifiable. Preserve diagnostic worker-count overrides and benchmark actual throughput and memory use on physical hardware, including the two-drive test below. **Acceptance:** independent destination readback remains complete, cancellation still stops the run, and unknown topology gets a conservative policy rather than invented independence.

- [ ] **Review unknown-drive backup claims.** `BackupIndependencePolicy` currently counts each destination whose physical disk identity cannot be resolved as a separate backup; this was an intentional product choice pending positive evidence of a shared disk, not a confirmed defect. A first bounded slice now records resolved identity groups separately from unresolved destinations and quietly notes uncertainty beside the single-card Setup destination count. It does not change the verdict, the saved count or staged-queue claims. Next decide separately how many copies verified and how many physical devices are *known* to be independent, then make staged setup, completion, safe-to-erase wording, History and reports say only what the evidence supports. Do not silently demote every iPhone/iPad file-provider destination or change the existing verdict without a product decision. **Acceptance:** known-shared, known-distinct and unknown identities, plus RAID/composite, network and mobile-provider cases, have explicit tests and consistent user-facing claims; storage scheduling does not treat unknown devices as proven independent.

- [ ] **Bounded source-read retries and “Don't format the card” warnings.** Cover both source changes and read instability, separately from destination failures. Retry transient source I/O failures a small, bounded number of times and record each attempt and reason. Separate verified backup contents from source-media health: a recovered read must still warn against formatting or reusing an unstable card until investigated. Distinguish that from a failed backup. Explore chunk retries only with proven hash continuity and source identity checks. **Acceptance:** injected recoverable and persistent faults produce accurate counts, evidence and warnings; retries never hide changed data or turn exhaustion into success.

- [x] **Explicit interrupted-transfer recovery.** Build on existing journal retries, identity checks and independent verification before whole-file reuse. Show reused, recopied, failed and pending files per destination; retain the old attempt. **Acceptance:** no unproven existing file is overwritten, original volume/folder identity remains required, and the original attempt remains interrupted/unsafe; only a fully verified new attempt can earn a safe verdict. Describe complete-file recovery honestly; do not claim byte-offset resume.

- [ ] **Repair a failed destination from a verified sibling.** After recovery provenance is defined, investigate SSD A → failed HDD B repair without rereading the original card unnecessarily. Require authoritative file evidence, revalidate A, independently verify B, and record the original source, repair source and new attempt in reports/history. **Acceptance:** stale or changed sibling evidence cannot authorize a repair; existing unverified files are never overwritten; copies on the same physical device never count as independent backups.

- [x] **Check everything again at Start.** Existing engine preflight checks output roots, overlaps and access; journal preparation checks stored identities. Audit remaining gaps between selection, queueing and execution. Cover card/drive disconnect or replacement and two queued cards resolving to the same output folder (for example two “NO NAME” cards without a card number in the naming pattern). **Acceptance:** refuse unsafe starts before copying, explain why nothing was copied, and retain regressions for each gap found.

- [x] **Finish the card-untouched regression.** `SourceTreeUnchangedTests` already compares paths, contents, sizes, modification dates and permissions through the app executor in every verification mode, with reports and MHL enabled. The quick-win batch adds creation dates, ownership and extended attributes, plus cancellation-after-readback and report-publication-failure tests; coordinate with #16's real companion fixtures. **Acceptance:** the full source snapshot is unchanged after success, cancellation and failure; unsupported metadata checks are reported as such, not counted as passes.

- [ ] **Re-copy a newly written file that fails verification.** Investigate one automatic re-copy/re-verify, coordinated with recovery and sibling repair. **Acceptance:** replacement is limited to an output whose identity and ownership by this attempt are proven; never replace a file predating the run or one changed by another writer. Preserve the initial failure and retry outcome, and keep the verdict unsafe if retry fails.

- [ ] **One destination out of space.** Investigate pausing only that destination while the others finish, then revalidate space and identity before continuing. Today the failed destination is reported while others can finish. **Acceptance:** partial work remains visibly incomplete, cancellation works, and the overall verdict cannot become safe until every required backup verifies.

- [x] **Finish local terminal progress/outcome parity.** The engine withholds `.completed` and 100% when selected rows fail. The merged local slice adds an active Finishing state while MHL/report/journal evidence settles, keeps cancelled and unexpectedly interrupted wording distinct, and refuses a safe History/Finish verdict for missing, duplicated or copied-but-unverified selected results. Mac/iPhone/iPad shared presentation and focused cancellation/terminal tests cover this local slice; a percentage alone is never a success verdict. Future remote presentation and the signed-app fault walkthrough remain separate release gates.

- [ ] **Opt-in crash reports.** Investigate Apple's MetricKit crash/hang diagnostics, off by default, with no third-party service or automatic sending. Existing local diagnostic exports already record phases, cancellations, verification breadcrumbs and memory use; they cannot establish why a process disappeared.

## P2 — Evidence and interoperability

October 14 cloud progress: the independent ASC corpus added SHA-1/XXH128 unsupported-format fixtures and XXH64 lane/tail boundaries. Its reference runner passed 68 checks on Linux and macOS, including negative controls and unchanged originals. Swift consumer tests, fresh BitMatch output against the pinned reference, Mac tests and iPhone/iPad simulator suites also passed. October 17 adds an official reference-tool two-generation file-rename/directory-move fixture; the expanded runner passes 82 checks. Physical-media and signed-app checks still remain before a release. Interoperability and structural/history work below remain open.

- [ ] **Upstream MHL / source provenance.** Reuse `SavedChecksumCheck` where appropriate to offer source verification against accompanying classic MHL or ASC MHL evidence. Record “source arrived intact” separately from “BitMatch created verified backups.” Preserve original manifests. Current Check discovers ASC inventories under `ascmhl/`; standalone classic-MHL discovery and an upstream transfer verdict still need work. **Acceptance:** incomplete, mismatched, malformed and unsupported evidence gets an honest separate verdict; a failed provenance check never becomes success and never prevents preservation of damaged-but-irreplaceable media.

- [ ] **MHL interoperability corpus.** The permanent corpus covers official ASC reference-tool MD5/XXH64 output, two generations, unsupported C4/SHA-1/XXH128, Unicode/whitespace paths, nested inventories, damaged records, a recorded file rename and directory move, and report compatibility. The classic-v1 boundary is handcrafted and explicitly identified as such. See [the validation record](EVIDENCE_COMPATIBILITY_VALIDATION.md). Continue with redistributable, independently attributable classic MHL and representative output from another implementation before claiming broad interoperability. Keep multi-file saved-record and relative-path regressions current. **Acceptance:** validate with independent reference implementations, record fixture provenance/licensing and expected outcomes, and never silently treat unsupported evidence as fully verified.

- [ ] **ASC MHL structural verification.** After the corpus establishes expected semantics, extend Check to validate supported root/directory hashes and detect renamed, moved, missing or structurally altered content. **Acceptance:** distinguish file-content verification from structural verification; older manifests without structural evidence remain usable with an explicit scope. Do not claim full history verification before the chain semantics are implemented and independently tested.

- [ ] **Extend existing MHL histories.** Check already verifies recorded file contents; generating another history generation is still unsupported. Coordinate with structural verification and the reference corpus. **Acceptance:** preserve existing histories, validate the new chain independently, and ensure interruption cannot expose a partial generation as complete. Keep the current refusal until this is proven.

- [ ] **Measure before changing the transfer hash.** The saved-checksum reader supports XXH64; transfer verdicts currently rely on SHA-256. First measure complete runs through MHL/report publication, per-stage CPU and I/O, and peak memory on real drives. A cheaper hot-path hash saves time only if it replaces measured work; adding it alongside unchanged per-byte SHA-256 cannot remove that work and may slow the run. If substitution is proposed, compare collision/assurance properties, source and destination readback coverage, old evidence, report labels and interoperability; keep the chosen manifest's required digests valid. A non-cryptographic match must not silently inherit the current SHA-256 safe verdict. **Acceptance:** a repeatable end-to-end gain on relevant hardware and a documented safety/compatibility decision, or an explicit decision to keep SHA-256. No change to the default algorithm on a micro-benchmark alone.

- [ ] **Decide when compatibility digests are computed.** Inventory SHA-256, MD5 and SHA-1 use across the four transfer modes, reuse/Compare/Check, reports, ASC MHL and SFTP. SHA-1 is not a current transfer-mode digest; Thorough explicitly uses MD5 as a second verdict digest, and Standard also computes MD5 during existing reads for the default ASC MHL handoff without using it for its SHA-256 verdict. Measure the incremental CPU cost before adding an option. Offer extra compatibility-only digests by explicit choice where the selected evidence format does not require them; do not silently change what Thorough verifies or omit a digest from an enabled ASC MHL record. Reuse verified readback evidence only where the filesystem identity check makes that safe; preserve the deliberate fresh destination read on exFAT. **Acceptance:** generated records still pass independent reference checks, old saved evidence remains readable, each result distinguishes verdict digests from recorded-only digests, and optional interop choices stay out of the everyday setup unless a measured benefit or user need justifies them.

## P2 — BitMatch Remote (proposed; after transfer reliability and data integrity)

Keep the existing universal iPhone/iPad app's three local modes—Copy & Verify, Check and Master Report—fully functional, including standalone USB-C offloading. Add **Remote Mac** as a fourth mode in that same app, starting with read-only monitoring; choose a host inside Remote rather than adding a host selector to every local screen. Optimize iPad for a persistent DIT-cart control surface and iPhone for compact monitoring. The Mac remains the sole authority for its storage, transfers, verification, queue, journal, reports and safe-to-erase verdicts. Reuse `SharedAppCoordinator`, shared readiness and presentation models; do not create a second transfer engine or simulate UI clicks. Remote hosting remains free and open source on Mac. A **$5.99 lifetime** universal iOS/iPadOS price is a hypothesis to test, not a settled release decision; avoid subscriptions, feature tiers, accounts and an internet requirement, and use TestFlight before release.

- [ ] **Phase 1 — Mac menu bar companion.** The first implementation is merged: `MenuBarExtra` shows active stage, progress and per-destination status or the most recent result; closing the main window during a transfer hides it, Open BitMatch restores that window, and Quit retains the transfer guard. Local automated tests cover a transfer completing while hidden and reopening the intended window. Finish a signed-app walkthrough of the menu, window close/reopen, Quit, and a newly detected card before calling this release-ready. Later show connected clients inside the menu; a lost remote connection is not a transfer failure. Keep one normal Mac application, without a helper or daemon.
- [ ] **Phase 2 — Read-only remote monitoring.** The fourth mobile mode discovers and selects a Mac over Bonjour, then uses an authenticated, encrypted local-network connection over Wi-Fi or wired Ethernet; explicit Mac opt-in, one-time code/QR pairing, persistent device identity, connected-client visibility and revocation. Handle networks that block discovery or device-to-device traffic explicitly. Send an authoritative initial snapshot, bounded/coalesced live updates and paginated/on-demand recent history. **Acceptance:** client disconnection or mobile background suspension never affects Mac work; Mac sleep/quit makes the remote view visibly stale, never falsely complete. Reconnect obtains a fresh snapshot, and host/session identity plus revisions prevent missed or old events from becoming current results. Never infer completion from 100% progress or attach a cached safe verdict to a newly connected card. No unauthenticated control or automatic diagnostic/report uploads; minimize private names and paths, and consider display-only privacy mode.
- [ ] **Phase 3 — Remote setup, queue and Start.** Display Mac-attached sources, authorized destinations, capacity, availability and the Mac's readiness result. Select, enqueue and start through existing coordinator operations using opaque host-validated storage identities, not raw paths. Any required macOS folder authorization stays on the Mac. **Acceptance:** authenticated commands target the intended host and current operation/queue revision, revalidate source/destination and physical-device identities at execution, and preserve preflight, no-overwrite and independence rules. Stable request IDs make duplicate/delayed Start requests return the existing result rather than create work twice. Disconnected clients cannot submit commands.
- [ ] **Phase 4 — Operational controls and outcomes.** Add supported pause/resume, retry, queue management and cancellation with explicit confirmation. Show actual engine stages, destination-specific progress, measured throughput/ETA where available, warnings and authoritative final outcomes. Browse recent history without automatically fetching PDFs. **Acceptance:** stale or out-of-order mutations are rejected or safely reconciled; retries preserve the old attempt, and remote controls cannot bypass any Mac safety rule.
- [ ] **Phase 5 — Connectivity enhancements.** Test powered USB-C Ethernet hubs and network changes. Investigate direct Mac–iPad USB-C app connectivity with a small public-API proof of concept before promising support; ordinary cable attachment is not assumed to provide networking. Keep Wi-Fi/Ethernet supported if no reliable public-API USB transport exists. Consider saved hosts or multiple-host monitoring only with user evidence; no multi-host coordination. Bluetooth is deferred.
- [ ] **Remote validation and distribution gates.** Automate disconnects during copy/verify, host restart, client suspension, missed events, simultaneous reconnects, duplicate/delayed/out-of-order commands, stale/replaced/removed storage, changed queue items, failed preflight, source-target overlap, overwrite attempts, physical-drive independence, unauthorized/revoked clients, cancel during verification and retry after interruption. Stress thousands of events, slow/multiple clients, large history and repeated disconnects during large transfers; event queues must stay bounded and networking must not block the pipeline. Validate local-mode parity, iPhone/iPad layouts, actual sandbox/file-provider constraints, local-network privacy/Bonjour declarations and background limits on Apple devices. Keep synthetic, simulator and physical-device results separate.

Remote scope excludes screen sharing, arbitrary filesystem browsing, remote shell, cloud relays, accounts, camera-card formatting, automatic remote eject and facility management. Preserve the existing media-management exclusions below. This roadmap records a proposal, not implemented functionality or a release promise.

## Validation, accessibility and release readiness

These remain ongoing gates, not optional features. Use disposable data and retain failures and skipped checks alongside passes.

- [ ] **Physical hardware reports.** Ask users to fill in the [hardware report template](HARDWARE_REPORT_TEMPLATE.md) for their cameras, readers, drives and connections. - [ ] **End-to-end two-drive benchmark.** Start with a representative disposable card containing large clips and small sidecars, one source and two physical destinations on known connections, through `RealCopyBenchTests` and the signed app. Compare Standard and Thorough first; expand verification modes, APFS/exFAT/FAT and drive combinations only when evidence warrants it.
