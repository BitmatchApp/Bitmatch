# BitMatch competitive engineering audit

Status: written against `92044955`. Since then, 0.2.14 fixed two of its findings: journal writes are now durable (flushed to the drive, then renamed, then the folder flushed), and special files are no longer silently skipped.

Date: 2026-11-26. Read-only. BitMatch branch audited: worktree `hdd-aware-workers` (HEAD `92044955`). Upstream clones: SD-Offload (HEAD = v1.7.29, 2026-11-20), paiml/copia, lucuma13/mhl-suite, ascmitc/mhl, all cloned into the scratchpad `competitors/` folder and read as untrusted data (never built or executed).

Paths below: `BM:` = BitMatch repo root; `SDO:` = SD-Offload clone; `COPIA:`, `MHLS:`, `ASCMHL:` = the other clones. Line numbers are from the files as read today.

Severity scale: **proven bug** (code shown misbehaves), **likely gap** (no handling and no test; needs a real-world check to confirm), **theoretical** (safe today; an improvement in evidence, UX or speed).

## Executive summary: top 5 actionable items

1. **Fixed after the audit (next release, on the branch):** measured on a macOS SMB share, `linkat` returns `ENOTSUP` and `renameatx_np(RENAME_EXCL)` is unsupported; destinations on measured filesystems without hard links (SMB, confirmed by the volume's own capabilities) now publish directly under the status marker; unmeasured filesystems keep the link path and fail closed if the link is refused, and ASC MHL histories on `smbfs` are claimed the FAT way with a `0001_BitMatch_DIRECT_` manifest. The mounted-filesystem matrix passes 12/12 against the share (`docs/TRANSFER_MATRIX.md`). Original finding: **SMB/NAS destinations are almost certainly unusable, and nothing tests them (likely gap, high impact).** `PinnedDestinationDirectory.open` enables the no-hard-link publication path only for FAT-family filesystems (`isFATFamily`, `BM:Packages/BitMatchEngine/Sources/BitMatchEngine/File/DestinationWriter.swift:562-571`). Every other filesystem publishes with `linkat` and fails the file when `linkat` returns `ENOTSUP` (`DestinationWriter.swift:439-461`, message "This destination filesystem cannot safely publish files"). macOS `smbfs` and WebDAV do not support hard links, so a NAS backup would fail every file (fail-closed, so no data risk, but the thesis promises NAS as a backup target and `docs/THESIS.md` already says "Not yet checked against a real NAS/SMB mount"). SD-Offload (`SDO:Sources/OffloadEngine/DestinationWriter.swift:7-12`, `SessionRunner.swift:472-480`) hit exactly this with `RENAME_EXCL` in v1.7.13 and switched network filesystems to `O_EXCL` creation in v1.7.14. Recommendation: add an opt-in live-share test (like `PhysicalDriveTransferTests`, driven by `BITMATCH_SMB_ROOT`) that proves (a) whether `volumeUUIDString`/`volumeCreationDate` exist on `smbfs` (journal admission needs one, `TransferJournal.swift:88-117,175-181`), (b) which errno `linkat` returns, (c) that the existing direct-final path with `TransferStatusMarker` works there, then extend the direct-final decision to a measured no-hard-link list (`smbfs`, `webdav`, `afpfs` once measured). Keep the fail-closed default for unknown filesystems.

2. **Symlinks, FIFOs, sockets and device nodes on a card are silently dropped and the verdict still reads "All files copied and verified" (proven silent skip; same code shape as Copia's #46/#49 bug).** `CardSource.walk()` classifies only `S_IFDIR` and `S_IFREG` and has no `else` arm (`BM:…/File/CardSource.swift:353-393`; `TreeEntryKind` has two cases, `:135-138`); every consumer (manifest, completion re-scan, coverage, Compare, ASC MHL) uses that one walker, so `totalFiles` excludes the entry and `TransferCompletion.verdict` has nothing to miss (`TransferPipeline.swift:744-745,1549-1554`; `TransferCompletion.swift:441`). BitMatch's own `SharedFileOperationsEdgeCaseTests.testCopySkipsSymlinkEntries` (`:43-92`) pins the skip without asserting any warning. Copia fixed the identical pattern in `f0a99dc` by classifying every entry kind and refusing loudly. Camera cards rarely carry such entries, so field impact is low, but promises 2 and 3 say the user must be told. Recommendation: add `TreeEntryKind.unsupported(kind:)`, emit an excluded row per entry (reuse the AppleDouble exclusion plumbing, `TransferPipeline.swift:751-762`), make the record `issues` with "N entries cannot be copied … Keep the source", report kind mismatches and directory-presence differences in Compare, and add source-tree tests with `mkfifo`, a bound socket, a symlink and a dangling symlink. Never open or follow them. Section 8 has the full per-type table (dataless files, AppleDouble and metadata dirs are already handled well).

3. **The transfer journal is not power-loss durable (likely gap, low-to-medium impact).** `TransferJournal.persist` writes with `Data.write(options: .atomic)` (`BM:…/TransferJournal.swift:1084-1089`): rename, no `fsync`, no parent-directory `fsync`. SD-Offload's `JSONIO.saveDurable` (`SDO:Sources/OffloadCore/JSONIO.swift:80-113`) does temp + `fsync` + `rename` + parent `fsync`. BitMatch's `ProcessDeathRecoveryTests` prove kill -9 recovery, which the page cache survives; a power cut or kernel panic can drop a `running` or `completed` record entirely, so the user loses the "Interrupted" banner or a finished record's evidence (the on-destination reports survive). Fix is ~20 lines, no behavior risk: fsync the temp file and the directory in `persist`. Add a regression that opens the journal through an `F_FULLFSYNC`-counting hook, or at least asserts `persist` calls `fsync` via a seam.

4. **No stalled-transfer signal (theoretical/UX, medium impact for NAS and dying cards).** SD-Offload tracks `secondsWithoutProgress` per verification pass and drops the ETA after 10 s of silence (`SDO:Sources/OffloadEngine/VerificationProgress.swift:21-24,84`; `SpeedMeter.swift:19-50`), and labels NAS waits ("Waiting for NAS file information", `SessionRunner.swift:396`). BitMatch's `ProgressPresentationModel` (`BM:Shared/Core/ViewModels/ProgressPresentationModel.swift:280-304`) computes time left from a 10 s rolling window of *active* intervals only, so during a stall the last good rate is shown indefinitely and the time-left stays frozen; `OperationProgress` carries no last-activity timestamp (`BM:…/Models/OperationProgress.swift`). `docs/TODO.md:88` already asks that "mid-copy access loss must report interruption rather than silently stall". Recommendation: add `lastIOUptime` to the engine's progress (the `TransferIOMeter` already records per-call uptimes, `Models/TransferIOProgress.swift:58-90`), show "No data moved for N s" after 10 s and blank the time-left; test with a `FanOutHooks.beforeWrite` that blocks for 15 s (the hook infrastructure exists in `FanOutTests`).

5. **Interrupted transfers lose per-file evidence gathered before the crash (theoretical, evidence quality).** BitMatch records `ResultRow`s only at `finish`/`interrupt`/`cancel` (`TransferJournal.swift:882-1052`; callers `SharedAppCoordinator.swift:2575,2766,2781`). After process death the record becomes `interrupted` with whatever rows were last written, which for a killed process is none (`TransferJournal.swift:385-391`). SD-Offload flushes each file's verified state and source hash to the journal as a milestone (`SDO:…/Journal.swift:266-275,286-290`; `StagingStore.swift:209-213`). BitMatch's retry already re-verifies every existing destination file byte-for-byte before reuse (`ExistingDestinationReuseTests`, `docs/QUEUE_RECOVERY_VALIDATION.md`), so safety is equal; the gap is that History cannot show "412 of 1,200 files had verified before the crash". Recommendation (keep the safety rule): periodically checkpoint the live rows into the running record (every N rows or 5 s) marked as *provisional*, never counted toward the verdict; a `JournalStartupPersistenceTests` case should prove provisional rows never flip an `interrupted` record to `completed`.


Items in sections 6-11 are lower priority: verification-phase time left, mid-transfer card reinsertion, IOMedia generation identity, ASC MHL `<ignore>` patterns and xxh128 in Check, classic MHL `xxhash64be` (none of the four mainstream classic fixtures is readable today), NFD round-trip validation, journal `.bak`, chunk size on SMB, and the per-file ETA overhead model.

## 2. Card identity and reconnect handling

**SD-Offload.** Identity = volume UUID (or synthesized `"\(name)#\(mediaSize)"` when FAT32 reports none, `SDO:Sources/OffloadEngine/CardWatcher.swift:285-292`) + kernel mount snapshot from `getmntinfo(MNT_NOWAIT)` (`f_fsid`, `CardWatcher.swift:223-245`) + IOMedia registry entry ID (`CardWatcher.swift:296-304`, `CardMountSnapshot.swift:25-27`). A session additionally writes a random token file to the card (`Models.swift:245-249`) and rechecks it before erasing (`WipeGate.swift:106`). Journal lookup for resume is by `cardVolumeUUID` only (`Journal.swift:84-105`), so two FAT32 cards with the same label and size share an identity until the token is checked.

**BitMatch.** `LocalTransferResource` records volume UUID or, for UDF, `name|capacity|volumeCreationDate` (all three required, `TransferJournal.swift:175-181`), the `fileResourceIdentifier`, folder `creationDate`, and on macOS a device-free `fileIdentifier` trusted only on local, non-cloud volumes with a birth time (`TransferJournal.swift:16-62`). Admission (`prepareToRun`, `TransferJournal.swift:491-512`) resolves the bookmark and requires volume identity, folder identity and creation date to match (`validateIdentity`, lines 88-117); a record without identity is refused (`unverifiableIdentity`). Reauthorization rejects a different folder or volume (`validateReauthorization`, 638+). Live detection uses `st_dev + volumeUUID` as a best-effort key that "never authorizes a transfer by itself" (`BM:BitMatch/Core/Services/VolumeMonitorService.swift:549-603`).

**Assessment.** BitMatch's durable identity is stronger than SD-Offload's (three-part fallback vs name#size; creation date; file ID). SD-Offload's live-detection identity is stronger in one respect: the IOMedia registry entry ID distinguishes a *new physical medium* even when the reader reuses BSD name, UUID and fsid (`CHANGELOG.md` 1.7.23). BitMatch's `VolumeMonitorService` compares `st_dev` + UUID, which can be reused after a fast swap. Because BitMatch gates every transfer on the journal identity and never erases, this is **theoretical**. If card auto-source selection is ever extended to auto-start, add `IORegistryEntryGetRegistryEntryID(DADiskCopyIOMedia(disk))` to `VolumeMonitorService.MountedVolume.identity` and a `VolumeMonitorReconciliationTests` case for "same UUID, new media ID".

**NAS identity (likely gap, see item 1).** `volumeIdentity` needs `volumeUUIDString` or `volumeCreationDate`. SD-Offload's authors note "volumeUUID is unreliable on smbfs" (`SDO:Sources/OffloadEngine/NASLocator.swift:31-33`) and identify the share with `statfs` `f_mntfromname` + `f_mntonname` (`NASLocator.swift:47-66`; `Statfs.swift:16-36`), detecting a "ghost" local folder at the mount point (`.ghostLocalFolder`) and a different share mounted at the same path (`.wrongShare`). BitMatch's `testDetachedDestinationAfterPreflightFailsWithoutWritingMountpoint` covers the ghost-folder case via pinned descriptors, but the identity fallback for a share with no UUID and no creation date is untested. Recommendation: in the live-share test, assert what `URLResourceValues` returns on `smbfs`; if both are nil, add a network-volume identity of `mntfromname` (server, share) + `mntonname`, matching the UDF design pattern, and a `ReconnectIdentityTests` case.

## 3. Durable per-file verification checkpoints

**SD-Offload.** `FileState` is a per-file state machine (`SDO:Sources/OffloadCore/Models.swift:69-135`) persisted in the session JSON; `setSourceHash` and `setSessionState` flush immediately, other transitions coalesce to a 1 s flush (`Journal.swift:266-275,286-290,338-353`). On reopen, in-flight states roll back (`crashRemap`: copying→pending, uploading→stagedVerified, `Models.swift:108-114`; tested by `JournalTests.testResumeAppliesCrashRemap`). Illegal transitions coerce to `.failed` and block the wipe (`Journal.swift:238-242`; `JournalTests.testIllegalTransitionCoercesToFailedAndBlocksWipe`). Staging is freed only after the checkpoint is `flushNow`-ed (`StagingStore.swift:209-213`). Crucially, the checkpoint is **not** trusted for the final decision: `DestinationVerifier.verify` re-reads every destination file uncached before any erasure (`DestinationVerifier.swift:4-34`; `TransferSafetyRegressionTests`).

**BitMatch.** No per-file checkpoint during a run. The record carries `plannedFileCounts` from `recordPlan` (`TransferJournal.swift:703`), and the full `ResultRow` list only at the end. On retry, every pre-existing destination file is re-hashed (and byte-compared in Paranoid) before reuse (`DestinationWriter` reuse path; `ExistingDestinationReuseTests`, `PublicationReuseTests`), and an incomplete plan can never become `completed` (`hasCompletePlannedResults`, `TransferJournal.swift:1010-1029`).

**Assessment.** Safety-equivalent: both re-read before trusting. BitMatch does more I/O on retry than SD-Offload's resume (it also re-hashes the *source* unless `sourceReadEvidence` is reused; `DestinationWriter.swift:1968-1990`), which is the price of not trusting checkpoints and should be kept. The gap is evidence/UX (item 5). Do **not** adopt SD-Offload's `skippedDuplicate`-from-checkpoint behavior for verdicts.

## 4. Interrupted SMB/NAS transfers and recovery

**SD-Offload** (`SessionRunner.swift:395-565,720-800`; `NASLocator.swift`): health check by `statfs` type ∈ {smbfs, afpfs, nfs, webdav}, exact mount point, expected `f_mntfromname`, read-only flag; `waitForHealthyNAS` blocks uploads with a visible "share not mounted — refusing to write" attention item and attempts one NetFS remount with backoff; per-file `O_EXCL` create on network filesystems because `RENAME_EXCL` is rejected by many SMB servers (v1.7.14); `F_PREALLOCATE` skipped on smbfs; `F_FULLFSYNC` is `ENOTSUP` on smbfs, so read-back with `F_NOCACHE` is the durability proof; `ENOTSUP` on a destination op stops retries instead of re-uploading (`handleHop2Error`, line 800). Known limitation they document: `F_NOCACHE` read-back proves the server's copy, not platter durability.

**BitMatch.** Publication: `linkat` then unlink (`DestinationWriter.swift:439-461`); direct-final with `TransferStatusMarker` only when `isFATFamily` (`:562-571`) or forced by a test hook. Flush: `F_FULLFSYNC`, falling back to `fsync` on `ENOTSUP` (`:417-432`) — correct for smbfs. Read-back: `F_NOCACHE` required (`:368,390,662`) — `F_NOCACHE` is a VFS-level vnode flag and succeeds on smbfs, so this is fine. Free-space preflight via `volumeAvailableCapacity` — fine. Journal admission: see section 2. No health wait: a share that drops mid-run fails each remaining file on open/write and the record becomes `interrupted`; the user remounts and retries, which re-verifies existing files. That is acceptable behavior.

**Finding (likely gap, high impact; executive item 1).** Unless macOS `smbfs` implements `link(2)` (it does not, to the best of my knowledge, and WebDAV certainly does not), every file to an SMB share fails at publication with "This destination filesystem cannot safely publish files; choose a different backup folder". Fail-closed, so no false green, but the feature is effectively absent and `BackupTargetPolicy` explicitly allows a network share root to be restored as a backup (`ARCHITECTURE.md:124`; THESIS follow-up marked done "Not yet checked against a real NAS/SMB mount"). The fix is small because the FAT-family direct-final path with the durable status marker is already the designed answer for filesystems without hard links (`docs/EXFAT_PUBLICATION_DESIGN.md`): extend `isFATFamily` into `lacksAtomicNoReplaceLink` with `smbfs`, `webdav` (and `afpfs` if measured) after a live test confirms behavior, and record the fstype in `TransferDiagnosticStore`. Do not adopt SD-Offload's inverse rule (`!["apfs","hfs","exfat","msdos"].contains`) which treats unknown filesystems as exclusive-create capable; BitMatch's fail-closed default for unknown types is better.

**Recommended regression test.** `LiveSMBDestinationTests` (opt-in, `BITMATCH_LIVE_SMB_ROOT`, disposable subfolder, modeled on `PhysicalDriveTransferTests` and SD-Offload's `testOptInLiveSMBTrashAndRecoveryUsesOnlyDisposableFiles`): one Standard transfer with two destinations (local APFS + share); assert every row verified, MHL published, `F_FULLFSYNC` fallback taken, and that `prepareToRun` succeeds on the record after `TransferJournal` reopen. Second case: unmount the share mid-copy via a `FanOutHooks.beforeWrite` that runs `umount` on the disposable mount (or simply mark the destination unreachable), assert `interrupted`, remount, retry, assert reuse rows and clean verdict.

## 5. Preservation of completed verification evidence

**SD-Offload.** Journal records keep `sourceHashHex` per file for 300 sessions (`Journal.swift:116-150`), `previouslyVerifiedDestination` treats a missing previously verified NAS file as a deliberate deletion that blocks recreation (`Journal.swift:187-213`; `TransferSafetyRegressionTests.testPreviouslyVerifiedButNowMissingDestinationBlocks`), and a `DestinationDeletionStore` ledger records in-app deletion intent (v1.7.27). Verified evidence is kept only in the app's journal; nothing is written next to the files.

**BitMatch.** Evidence is written where it can be handed to someone: CSV/JSON/PDF report under `Reports/`, checksum manifest, ASC MHL history with chain (`EvidenceWriter`, `ASCMHLGenerator`), plus the journal rows and `sourceFingerprint` for `matchingVerifiedRecord` (`TransferJournal.swift:973-983`) and `SavedChecksumCheck` to re-check against saved reports. `EvidenceWriterCommitOrderTests`, `EvidenceGoldenTests`, `EvidenceCompatibilityTests` and `VerificationScopeEvidenceTests` cover it. BitMatch is clearly ahead here; the "deleted destination is not recreated" rule is NAS-library semantics and is **not** wanted in an offload tool (a retry should recreate a missing backup file and say so).

**One gap (theoretical).** Evidence written *before* a crash (rows in memory, spilled by `ResultsOverflowService` past 5,000 rows) is lost with the process; see item 4. Also `TransferDiagnosticStore` is append-only with a directory lock (`TransferDiagnosticStore.swift:305-404`) — good — but its `append` uses `FileHandle` writes without `fsync`; acceptable for diagnostics.

## 6. Stalled transfer detection and ETA accuracy

**SD-Offload** (`SpeedMeter.swift`, `SpeedMath` in OffloadCore, `VerificationProgress.swift`, `SessionRunner.sampleAndEmit` lines 835-911): 10 Hz sampler; per-stage EWMA τ=5 s; per-stage `ETAWindow` that only counts intervals with bytes, needs warm-up (`ETAMath.isWarm`: seconds and bytes or files), and expires after 10 s without bytes; `OverheadModel` learns per-file fixed cost; ETA = max(card read, NAS write) + last-file tail, verify stages deliberately excluded because their bursty EWMA decays to zero and explodes the quotient (comment at lines 858-863); `clampETA` rejects >72 h, NaN, inf, negative (regression for a 53,446-hour display); display smoothing τ=3 s; `secondsWithoutProgress` ≥10 s nils the verification ETA and the UI shows a warning (CHANGELOG 1.7.14).

**BitMatch** (`ProgressPresentationModel.swift:215-335`, `TransferProgressPresentation.swift:177-324`, `TransferIOMeter` in `Models/TransferIOProgress.swift`): ticks at most every 120 ms; EMA for displayed speed; time left = remaining planned copy bytes / rate over the active intervals of a 10 s rolling window; "Estimating…" until 2 s of copying measured; nil when planned bytes are unknown or copied. Verification time is never estimated (thesis decision). `TransferIOMeter` measures the union of active I/O calls so fan-out waits don't skew per-destination rates.

**Assessment.**
- Decay-to-zero explosion: BitMatch is immune by construction (active intervals only). No action needed; an upper clamp is cheap insurance (theoretical).
- Stall: **gap (UX, medium).** A hung card or share freezes the display at the last good rate; nothing says "no data moved for 30 s" (item 4).
- Verification tail: after the copy finishes in sequential-verify mode (or Thorough/Paranoid with large files), BitMatch shows no time left at all while verification can run for a long time. SD-Offload estimates the tail from the write rate ("SMB read-back is at least as fast as write"). A measured verify-read rate from `TransferIOMeter` (`.readingBack`, `.sourceHashing` phases already exist) could drive a "verifying, about N min" estimate without a benchmark and without violating the thesis rule (observed speed only). Theoretical.
- Per-file overhead: theoretical; many-small-file ETAs are optimistic.

Suggested tests: `ProgressPresentationModelTests.testStallBlanksTimeLeftAfterTenSecondsAndReportsSecondsIdle`; `testVerifyPhaseTimeLeftUsesObservedReadbackRateOnly`.

## 8. Unexpected filesystem entry types and false-positive verification

**Copia's bug, confirmed from history.** Two commits: `2c0a3c8` (2026-08-22, "verify-before-delete, and the three data-loss bugs the rsync harness found", Closes #46) fixed symlink-to-dir, dangling symlink and empty dirs being dropped; `f0a99dc` (2026-08-23, "fix(walk): classify EVERY entry kind — a FIFO was lost and then certified identical", Refs #46/#49) fixed FIFO/socket/device. The buggy walker (`git show 2c0a3c8^:src/bin/copia/transfer.rs:17-22`):

```rust
if path.is_dir() && !path.is_symlink() { dirs.push(path); }
else if path.is_file() { files.push(rel); }
```

Anything neither a real directory nor `is_file()` fell out of the walk; `copia verify` shared the walk, so the entry was absent on both sides and counted as agreement (`COPIA:CHANGELOG.md:71-74`: `mkfifo src/pipe && copia sync` then `copia verify` printed "trees are identical — the source may safely be deleted", exit 0). The first fix attempt hung because `tokio::fs::copy` on a FIFO blocks. Fixed walker (`COPIA:src/bin/copia/transfer.rs:31-46`): symlink first, then dir, then *everything else*; fingerprints (`meta.rs:12-65`): symlink → blake3 of target string, regular → streaming blake3, other → blake3 of a kind tag ("fifo"/"socket"/"block-device"/"char-device"), never opened; delivery (`incremental.rs:419-434`) refuses non-file/non-symlink with a named error and the run fails ("N file(s) failed to transfer", `:112`). Still unhandled in Copia: hard links (no `nlink`/`ino` anywhere), **empty directories in verify** (`verify.rs:177-191` iterates files only, so a missing empty dir on the destination still passes exit 0 — a proven false positive within its own "trees are identical" claim), xattrs/sparse, anything macOS-specific.

Reference clone `ASCMHL:` is at `0fb61f1e` (2025-07-04, asc-mhl-1-2), the same commit BitMatch pins in `Scripts/ascmhl/validate_corpus.py:18`. `MHLS:` is mhl-suite v1.4.0 (`9304aef`).

### 9a. Unicode normalization

- **Reference (ascmitc/mhl): no normalization at all.** Names come from `os.listdir` (`ASCMHL:ascmhl/traverse.py:27-41`), serialized via `Path.as_posix()` (`utils.py:55-56`, `hashlist_xml_parser.py:280`), compared by Python `str` equality (`commands.py:633-641`, `hashlist.py:79-83`). NFC vs NFD = different file → "found new file" + "missing file". No non-ASCII test exists in its suite.
- **mhl-suite:** byte-exact first, NFC-equivalence fallback only when unambiguous (`MHLS:src/mhl_suite/osutils.py:356-414`, rationale `:325-335`); an identity carried by two real entries maps to none (`verify.py:336,355`); sealing refuses a tree with two names sharing one NFC identity (`osutils.py:339-353`, `classic_seal.py:201-219`), NFC only, not case.
- **BitMatch:** (a) writes `<path>` as the destination filesystem reports each component (`URLResourceValues.name`, `ASCMHLGenerator.swift:171-176`, escaped at `:287`), i.e. raw bytes, same policy as both competitors; no NFC/NFD conversion in any writer; there is no classic MHL writer (`ClassicMHLReader.swift:7`, read-only). (b) Check matches recorded paths to disk through Swift `String` keys, whose equality folds canonical equivalence (`SavedChecksumCheck.swift:256-298`), so NFC-recorded vs NFD-on-disk matches and the on-disk URL is what gets hashed; two on-disk names collapsing to one key throw `unreadableEvidence` (`:271-274`). Pinned by `ASCMHLCompatibilityMatrixTests.swift:78-125`. The classic reader rejects two `<file>` rows that are Swift-equal but byte-distinct (`ClassicMHLReader.swift:264-280`). Equivalent to mhl-suite's rule and more lenient than the reference. (c) A card with both "é" NFC and NFD is refused before copy by `SafetyValidator.validatePortableRelativePaths` (`SafetyValidator.swift:417-440`, key = `precomposedStringWithCanonicalMapping.lowercased(en_US_POSIX)`; `SourceFilenameAmbiguityTests.swift:6-50`), per directory, also for case-only pairs. The Unicode half matches mhl-suite's independent conclusion and is right for normalization-insensitive destinations (the pair cannot both exist after copy). The case-folding half is stricter than both competitors and over-strict only for case-sensitive destinations (case-sensitive APFS, ext4 over SMB); on default macOS/exFAT it prevents a silent overwrite. Defensible, not a bug.
- (d) **Proven mismatch with the reference: none on writing.** Theoretical, symmetric for all three tools: a destination later copied through a normalizing path (HFS+ NFD, `rsync --iconv`) fails the reference's byte-exact verify while BitMatch and mhl-suite still match. **Likely test gap:** `validate_reference.sh:40` and `Tools/ASCMHLFixture/main.swift:19` use "clip & café.txt" spelled NFC on APFS, so the script never proves an NFD round-trip; `MountedUnicodeSourceTests` (HFS+ image, `BITMATCH_UNICODE_HFS=1`) covers only the refusal path (`:117-133`). Recommendation: extend the HFS+ opt-in test to write a manifest from an NFD-stored destination and run the pinned reference verifier against it.

### 9c. Classic MHL v1.1

## 10. Performance and memory management

**SD-Offload `ChunkedIO`** (`SDO:Sources/OffloadEngine/ChunkedIO.swift`): 16 MiB chunks (comment: halves syscalls vs 8 MiB and gives smbfs larger sequential runs), one page-aligned `UnsafeMutableRawPointer` buffer per in-flight file reused across chunks (lines 46-50), raw `read`/`write` on a concurrent GCD queue with `withCheckedThrowingContinuation` (57-64), `F_NOCACHE` on one-pass source reads, `F_PREALLOCATE` with `F_ALLOCATECONTIG` then `F_ALLOCATEALL` fallback (104-111), SHA-256 of the bytes read computed during the copy so the card is read once (135). Verification reads 16 MiB with `F_NOCACHE`. Progress reported per 1 MiB read since 1.7.14. The 1.7.23/1.7.15 changelog entries describe moving blocking FS calls off the cooperative executor and using `getmntinfo(MNT_NOWAIT)` instead of `statfs(path)` on the DiskArbitration queue.

**BitMatch.** Copy loop reads 4 MiB with `FileHandle`/`Data` per chunk inside `autoreleasepool` (`DestinationWriter.swift:1205-1235`), hashes the source while copying for Standard and Paranoid (`sourceHasher`, `:1209-1213,1235`; Thorough deliberately re-reads) and reuses that evidence at verify time when the source identity is unchanged (`:1968-1990`), collects MD5 in the same destination read-back pass so ASC MHL needs no extra read (`:1992-1999`), `F_NOCACHE` everywhere, `F_FULLFSYNC` with fsync fallback plus parent-directory fsync. Fan-out writes one source read to every destination (`copyAllSafelyFanOut`, `TransferPipeline.swift:1026-1055`; `FanOutTests`), which SD-Offload does not do (its second destination is copied from staging). `ChecksumEngine` reads 4 MiB `Data` chunks (`ChecksumEngine.swift:146,247,287,329`). Buffer size was measured: `BufferSizeBenchTests` (64 KiB-8 MiB, 2 GB, opt-in) and `RealCopyBenchTests`; memory is probed by `StreamingMemoryProbeTests`, `VerificationMemoryTests`, `ASCMHLMemoryTests`, `SavedChecksumMemoryTests`, `CoordinatorManyFilesMemoryTests`, `PhysicalLargeFileAppMemoryTests`.

**Assessment.** Nothing in SD-Offload is demonstrably better; BitMatch reads the card once per run (fan-out) where SD-Offload reads it once per hop. Two items are worth a measurement, not a change:
- **Chunk size on SMB (theoretical).** SD-Offload's 16 MiB claim is about SMB2 request packing. BitMatch's bench covered up to 8 MiB on local media. If the live-SMB test from item 1 lands, run `BufferSizeBenchTests` with `BITMATCH_BENCH_DIR` on the share and only then consider a filesystem-dependent chunk size. Never change the hash-per-chunk discipline.
- **Allocation churn (theoretical).** `FileHandle.read(upToCount:)` allocates a fresh `Data` per 4 MiB chunk; SD-Offload reuses one aligned buffer. BitMatch's memory probes show this is bounded, and the `autoreleasepool` handles Foundation temporaries. A reusable `UnsafeMutableRawBufferPointer` with `pread` would cut allocator traffic for 100 GB clips; measure with `StreamingMemoryProbeTests` before and after.
- **`F_PREALLOCATE` (theoretical).** BitMatch does not preallocate the temp file. On APFS/HFS+ it would give contiguous extents and an early ENOSPC instead of a mid-file one; BitMatch already pauses the destination after the first ENOSPC (`DestinationWriter.swift:1060-1082`) so the benefit is small. Must be skipped on exFAT/FAT (where it is slow) and smbfs (`ENOTSUP`).

License for any reuse of `ChunkedIO`/`SpeedMeter` ideas: MIT, retain copyright notice. The ideas (EWMA with stall expiry, overhead model) are simple enough to reimplement without copying.

## 11. Lower-priority observations

- **Journal history growth.** SD-Offload trims to 300 sessions (`Journal.swift:129-150`); BitMatch keeps every record in one JSON array (`JournalStartupPersistenceTests.testTwentyThousandSavedResultRowsRemainUnchangedAcrossRepeatedOpens` proves 20k rows load; `HistoryAppHostScaleTests`). Theoretical: a year of daily multi-card offloads with per-file rows could make the single-file rewrite-on-every-mutation slow; consider archiving terminal records older than N months to a sidecar on request, never automatically deleting evidence.
- **`.bak` of the journal.** See section 1 row 5.
- **Attention items with errno.** SD-Offload preserves operation + errno through `NSError` (`RecoveryConsentTests.testWipeErrorPreservesOperationAndErrnoThroughNSError`); BitMatch records errno without paths in diagnostics (`ARCHITECTURE.md:288`) and canonical `failureReason` tokens — equivalent.
- **Power assertion.** Both take one (`PowerAssertion` vs `TransferKeepAwake`). Equal.
- **Follow-up (2026-11-26, after the `.DS_Store` skip).** Finder view files are now skipped only when proven and are listed on every backup, but the root folders `.Trashes`, `.Spotlight-V100` and `.fseventsd` (with `.TemporaryItems` and `.DocumentRevisions-V100`) are still skipped silently by `CardSource.enumerateRegularFiles`. They should be surfaced the same way, with rows and a summary line; `.Trashes` can hold deleted clips.
